# LLM Document Extractor

Тестовое задание LLM Engineer (задание А): извлечение данных из текста документа в JSON.
Интерфейс — простой CLI для TXT-файлов в UTF-8.

## Установка (Windows PowerShell, Python 3.11+)

Откройте терминал в папке проекта:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
Copy-Item .env.example .env
```

В `.env` укажите свой `OPENAI_API_KEY`. Модель по умолчанию — `gpt-5-nano`.
Извлечение делает один платный запрос. Автоматические повторы отключены.
Копируйте шаблон только если `.env` ещё не существует.
Если PowerShell запрещает активацию, используйте команды без неё:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe main.py data/documents/invoice_01.txt
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

С активированным окружением:

```powershell
python main.py data/documents/invoice_01.txt
python -m unittest discover -s tests -v
```

CLI выводит JSON в stdout; ошибки — в stderr с кодом завершения 1.
При отсутствии аргумента argparse возвращает код 2. Отказ модели, неполный
или невалидный ответ не выдаются как успешный результат. Тексты ошибок API
и ключ не печатаются.

## Структура

- `main.py` — точка входа.
- `extractor.py` — запрос OpenAI Responses API со Structured Outputs.
- `schemas.py` — Pydantic-модели `Document` и `LineItem`.
- `validators.py` — проверки БИН, итогов, НДС и дат составления по тексту.
- `eval.py` — оценка качества по документам и ручным эталонам.
- `data/documents/` и `data/expected/` — документы и эталонные JSON.
- `tests/test_schemas.py` — проверки схем без API.
- `REFLECTION.md` — место для итоговой рефлексии и архитектурного ответа.

## Правила схемы и принятые решения

Все ключи результата обязательны. Отсутствующие скалярные данные передаются как
`null`, неизвестный тип — `unknown`. Если позиций или предупреждений нет,
передаются пустые списки. `field_confidence` — словарь имён полей и чисел от 0 до 1;
в PDF приведён пример с `supplier_bin`, но закрытый перечень ключей не задан.

БИН — строка из ровно 12 ASCII-цифр; дата — существующая календарная дата
строго в формате `YYYY-MM-DD`. Валюта и тип документа ограничены значениями
из задания. Числа не принимаются в виде строк или булевых значений; NaN и
бесконечность запрещены. Лишние ключи запрещены, в том числе внутри позиций.
Знак сумм, количества и цены не ограничен: такого ограничения в PDF нет.

Pydantic проверяет структуру и значения. После него validators.py проверяет выбранные поля по тексту.
Промпт запрещает выдумывать сведения и вычислять суммы или НДС.
При противоречии значений одного поля с одной ролью возвращаются null и предупреждение.
Срок действия не является датой документа, промежуточный итог не является итогом к оплате.
«Без НДС» без числовой суммы означает vat_amount: null. Неоднозначный БИН с OCR-символами
не исправляется догадкой: null и предупреждение. Сумма прописью подтверждается для поддерживаемых русских и казахских числительных в тенге.
Промпт задаёт эти правила, а ограничения программной проверки описаны ниже.

Structured Outputs использует JSON Schema из Pydantic. API требует фиксированные
ключи объектов, поэтому в передаваемой схеме field_confidence ограничен ключом
supplier_bin, как в примере PDF. Валидатор заменяет оценку модели: 1.0 —
извлечённый БИН буквально найден после БИН/БСН, 0.0 — поле null. Это индикатор
совпадения с текстом, а не вероятность и не проверка принадлежности БИН поставщику. Основная Pydantic-модель допускает
и другие имена полей.

## Правила и ограничения валидатора

БИН подтверждается только как непрерывная строка из 12 цифр после метки БИН/БСН;
неподтверждённое заполненное значение удаляется с предупреждением. Если БИН
отсутствует и модель вернула null, это нормальная ситуация без предупреждения.
Валидатор не заполняет пропуски модели самостоятельно.

Строки итогов распознаются по меткам «Всего к оплате», «Итого к оплате»,
«К оплате», «Общая сумма», «Жалпы сомасы». Если таких меток нет, используются
«Итого»/«Всего». Разные значения на выбранном уровне означают конфликт и null.
Одинаковые суммы в разных форматах не конфликтуют. Поддержаны пробелы между
тысячами, точка/запятая для копеек, основные русские и казахские числительные
с масштабами «тысяча»/«мың», «миллион». Словесная сумма должна заканчиваться
«тенге»/«теңге», необязательно с цифровыми тиынами. Неизвестные слова,
нестандартные обороты, сокращения и другие языки не угадываются.

Даты составления проверяются после «от», «Составлено», «Дата документа»:
DD.MM.YYYY, YYYY-MM-DD или день + название месяца + год. Поддержаны полные
русские названия месяцев в родительном падеже и казахские названия месяцев.
Также распознаётся дата после '/' в заголовке счёта/акта с номером №.
Срок «действительно до» в эту проверку не входит. Разные распознанные даты
составления означают конфликт и null. Сокращённые месяцы и иные форматы
пока не поддерживаются. Неподтверждённая сумма или дата удаляется с предупреждением,
что может приводить к пропускам на неподдерживаемых форматах.

НДС проверяется в отдельной строке с меткой НДС/ҚҚС. Ставка процента может
стоять перед суммой, но не является суммой. Явный ноль допустим; «без НДС»
или «не облагается» без суммы не превращаются в ноль. Налог не вычисляется
из ставки. Неподтверждённое значение удаляется; разные явно указанные суммы
НДС означают null и предупреждение. Формулировки НДС внутри произвольного
предложения и сложные таблицы налогов не поддерживаются.

Свободные предупреждения LLM заменяются предупреждениями этих проверок.
Замечания о проблемах вне поддержанных проверок не сохраняются. Названия,
номера, валюта, количество и цены позиций пока не проверяются по тексту.
Классификация типа остаётся задачей модели; в промпте приведены явные заголовки.
Промпт отдельно запрещает выводить количество из факта наличия позиции и
копировать общий итог в отсутствующую цену. Универсальный парсер таблиц не добавлен.

## Mini-eval

С активированным окружением:

```powershell
python eval.py
```

Без активации:

```powershell
.\.venv\Scripts\python.exe eval.py
```

Один запуск проходит весь набор через `extract_document` и `validate_document`,
как CLI, и делает до 10 платных запросов, без автоматических повторов.
Перед запросами проверяются пары имён файлов, читаемость TXT и схемы всех эталонов.
При недоступности API, ошибке ключа/квоты или TLS запуск останавливается.
Другие ошибки API/ответа показываются отдельно. Для несовпавших полей выводятся
эталон, результат и, если он изменился, ответ до валидации. Сами ответы LLM
не сохраняются автоматически; для разбора ошибок сохраните вывод eval. Метрики рассчитываются только
по успешно обработанным документам; напечатаны число успехов, ошибок и необработанных.
Ошибка API не превращается в null и не считается пропуском поля. Неполный проход
не является результатом на всём наборе; код завершения при ошибках — 1.

Точность — число точных совпадений, делённое на число сравнений поля, включая null.
Сравниваются все 12 верхних полей. `line_items`, `field_confidence` и `warnings`
сравниваются целиком; порядок списков и текст строк учитываются, порядок ключей
JSON не учитывается. Дополнительно сравниваются `line_items.name`, `.qty`, `.price`
по порядку позиций. Отсутствующая позиция рассматривается как отсутствие её полей.
Текст предупреждения сравнивается буквально, поэтому другая формулировка даст ошибку.
Никакой подгонки эталонов или нечёткого сравнения нет.

Галлюцинация — значение заполнено при null/отсутствии в эталоне.
Пропуск — null/отсутствие при заполненном эталоне. Неверное ненулевое значение
снижает точность, но не относится к этим двум категориям. Пустые списки и словари
не равны null: лишнее предупреждение снижает точность warnings, но не считается
галлюцинацией по определению задания. Числа 100 и 100.0 равны; допуск для чисел
не вводится. Отчёт оценивает результат всего пайплайна после валидации, а не сырой ответ LLM.

Эталоны составлены вручную по TXT, без ответов модели и вызова валидатора.
Пробелы и переносы трёх документов из PDF нормализованы, сведения сохранены.
Название поставщика включает указанную правовую форму; двуязычное название
в invoice_03 сохраняется целиком. Названия позиций сохраняют язык исходника.
Перечень отдельных цен не суммируется в итог. Отсутствующее количество — null.
«НДС не облагается» без суммы — null, явно написанное «НДС: 0» — 0.
При конфликте дат/итогов соответствующее поле — null с предупреждением.
В эталонах используются единые формулировки предупреждений о конкретных проблемах.

валидатором: дата 2026-10-09 и сумма 340000 в invoice_03, сумма 120000 в invoice_10.
Теперь локальные тесты подтверждают сохранение этих значений. Эталоны не изменены.
Это проверка валидатора на заданном правильном входе, а не измерение качества модели.
