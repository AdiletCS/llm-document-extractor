# LLM Document Extractor

Тестовое задание LLM Engineer: CLI получает текст счёта, коммерческого предложения
или акта и возвращает JSON по фиксированной схеме. Используются Python, OpenAI API
и Pydantic; веб-интерфейс, база данных и обработка PDF не требуются для выбранного решения.

## Установка и API-ключ

Нужны Python 3.11+ и доступ к PyPI для установки зависимостей.
Откройте PowerShell в папке проекта:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
Copy-Item .env.example .env
```

Последнюю команду выполняйте только при первой настройке, если `.env` ещё нет.
Откройте `.env` и заполните ключ:

```dotenv
OPENAI_API_KEY=your_api_key
OPENAI_MODEL=gpt-5-nano
```

Настоящий ключ хранится только в `.env` или переменной окружения; `.env.example`
остаётся пустым шаблоном. `.env` игнорируется Git. Переменные окружения имеют
приоритет над `.env`; модель по умолчанию — `gpt-5-nano`.
Для реального извлечения нужен ключ с доступом к модели, баланс и сетевой доступ
к OpenAI API. Автотесты работают без ключа и сети.

## Запуск

CLI принимает путь к TXT в UTF-8 (также допускается UTF-8 BOM):

```powershell
.\.venv\Scripts\python.exe main.py data/documents/invoice_01.txt
```

Путь с пробелами заключайте в кавычки. JSON выводится в stdout, сообщение об ошибке —
в stderr. При ошибке файла, ключа, API, отказе модели, неполном или невалидном ответе
успешный JSON не выдаётся; код завершения — 1. Отсутствие аргумента обрабатывает
argparse с кодом 2. Текст исключения API и ключ в сообщения ошибок не включаются.

Тесты и оценка качества:

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
.\.venv\Scripts\python.exe eval.py
```

При желании активируйте окружение командой `.\.venv\Scripts\Activate.ps1`.
Тогда команды можно сократить до `python main.py data/documents/invoice_01.txt`,
`python -m unittest discover -s tests -v` и `python eval.py`.

CLI делает один платный запрос; полный eval — до 10. Автоматические повторы
отключены. При недоступности API, ошибке ключа/квоты или TLS eval останавливается;
прочие ошибки ответа отмечаются отдельно. Успехи, ошибки и необработанные документы
показаны явно. Метрики рассчитаны только для успешных ответов; сбои API не считаются
пропусками полей. При неполном проходе eval возвращает код 1.

## Как устроено решение

`main.py` читает TXT, `extractor.py` отправляет текст в OpenAI Responses API со
Structured Outputs, затем Pydantic проверяет JSON, а `validators.py` сопоставляет
выбранные поля с исходным текстом. После проверок результат ещё раз проходит Pydantic
и выводится пользователю. `eval.py` использует тот же пайплайн и сравнивает результат
с ручными эталонами. Модель получает документ как данные, с запретом выполнять его команды.

| Файл или папка | Назначение |
| --- | --- |
| `main.py` | Аргументы CLI, чтение TXT, вывод JSON и ошибок |
| `extractor.py` | Промпт, загрузка настроек и вызов OpenAI API |
| `schemas.py` | Схемы Document и LineItem со всеми полями задания |
| `validators.py` | Проверки БИН, итогов, НДС и дат документа |
| `eval.py` | Сравнение с эталонами и расчёт метрик |
| `data/documents/` | 10 исходных TXT |
| `data/expected/` | 10 эталонных JSON, составленных по текстам, а не ответам модели |
| `tests/` | 38 автотестов схем, проверок, ошибок и метрик |
| `requirements.txt` | Три зависимости: openai, pydantic, python-dotenv |
| `.env.example`, `.gitignore` | Шаблон настроек и исключения Git |
| `REFLECTION.md` | Ответы на пять вопросов и архитектурный вопрос |

## Принятые правила

Все 12 верхних ключей обязательны. Неизвестные скалярные сведения — `null`,
неизвестный тип — `unknown`, отсутствующие позиции и предупреждения — пустые списки.
БИН — строка из 12 ASCII-цифр; дата — существующая календарная дата YYYY-MM-DD.
Валюта — KZT, USD, EUR или null. Лишние ключи, числа в строках, булевы значения
в числовых полях, NaN и бесконечность запрещены. Ограничения на знак сумм и количества
не добавлены: их нет в задании.

Промпт запрещает выводить БИН из названия, подставлять текущую дату и вычислять
суммы, цены или налог из других полей. «Без НДС» и «не облагается» без суммы —
`vat_amount: null`; явно указанная сумма НДС 0 — ноль. Перечень отдельных цен не
суммируется в общий итог; отсутствующее количество не заменяется единицей.

Для `total_amount` приоритет имеют строки «Всего к оплате», «Итого к оплате»,
«К оплате», «Общая сумма», «Жалпы сомасы»; если их нет, проверяются «Итого»/«Всего».
Разные распознанные значения на выбранном уровне означают `null` и предупреждение.
Промежуточный итог и окончательная сумма сами по себе не являются противоречием.
Разные распознанные даты составления также означают `null` и предупреждение;
срок действия предложения не является датой составления. Разные явные суммы НДС
обрабатываются аналогично. Правило не зависит от порядка конфликтующих значений.

БИН подтверждается буквальным совпадением после БИН/БСН. OCR-символы не исправляются
догадкой. Неподтверждённые заполненные БИН, дата, итог или НДС удаляются с предупреждением;
пропуски модели автоматически не заполняются. Предупреждения модели заменяются
сообщениями программных проверок, поэтому проблемы вне этих проверок могут не попасть
в warnings.

`field_confidence.supplier_bin` — индикатор подтверждения: 1.0 при совпадении с текстом,
0.0 при null. Это не вероятность и не проверка принадлежности БИН поставщику.
API-схема ограничена этим ключом, как в примере задания: Structured Outputs требует
заранее определённых ключей объекта. Основная Pydantic-модель допускает другие имена.

## Тестовый набор и метрики

| Имя TXT и JSON без расширения | Источник и особенность |
| --- | --- |
| invoice_01 | Документ 1 работодателя: промежуточный итог, НДС и итог к оплате |
| offer_02 | Документ 2 работодателя: срок действия и отсутствующие реквизиты |
| invoice_03 | Документ 3 работодателя: два языка, OCR, сумма и месяц словами |
| act_04 | Собственный: акт и EUR |
| invoice_05 | Собственный сложный: нет БИН, номера, даты и НДС; USD |
| offer_06 | Собственный сложный: нет даты составления, БИН и общего итога |
| invoice_07 | Собственный сложный: противоречивые итоговые суммы |
| act_08 | Собственный сложный: противоречивые даты составления |
| invoice_09 | Собственный сложный: два языка, OCR и явно нулевой НДС |
| invoice_10 | Собственный сложный: сумма прописью и ставка НДС без суммы |

В первых трёх документах нормализованы пробелы и переносы PDF, сведения сохранены.
Названия поставщиков включают правовую форму; двуязычное название сохраняется целиком.
Эталоны не менялись ради совпадения с моделью или ограниченным валидатором.

Точность каждого поля — доля точных совпадений, включая null. Все 12 верхних полей
сравниваются отдельно; списки и словарь confidence — целиком. Дополнительно оцениваются
name, qty и price позиций по порядку, отсутствующая позиция означает отсутствие её полей.
Порядок ключей JSON не влияет на сравнение; порядок списков и текст строк влияют.
Числа 100 и 100.0 равны; числового допуска и нечёткого сравнения нет.

Галлюцинация в этом отчёте — заполненное значение при null/отсутствии в эталоне;
пропуск — null/отсутствие при заполненном эталоне. Неверное ненулевое значение
снижает точность, но не включается в эти два счётчика. Пустой список не равен null,
поэтому лишнее предупреждение снижает точность warnings, но не счётчик галлюцинаций.
Итоговые счётчики включают также поля позиций. Eval показывает конкретные расхождения
и исходный ответ до валидации, если он был изменён; автоматически лог не сохраняется.

Это результат на небольшом наборе после валидации, а не гарантия отсутствия галлюцинаций.
Ошибочные ненулевые значения и неточности текста возможны даже при нулевом счётчике.
Набор использовался при разработке; независимая проверка на новых документах ещё нужна.
Полный лог последнего ручного eval в репозитории не сохранён, поэтому точность по
отдельным полям здесь не приводится. При финальной подготовке API повторно не вызывался.

## Известные ограничения и дальнейшая работа

- **Смешанные языки.** На русско-казахских документах модель может ошибиться в типе,
  номере, месяце или названии позиции. Поддержаны лишь описанные ниже форматы дат.
- **OCR-ошибки.** Программа принимает готовый текст, распознавания сканов нет.
  Неоднозначные БИН не восстанавливаются; лишние пробелы и ошибки OCR могут приводить к null.
- **Суммы прописью.** Есть словарь основных русских и казахских числительных,
  масштабы «тысяча»/«мың» и «миллион», окончания «тенге»/«теңге» и цифровые тиыны.
  Другие языки, валюты прописью, сокращения и нестандартные обороты могут не подтвердиться.
- **Пропущенные позиции товаров.** Полнота списка зависит от LLM; отдельного парсера
  таблиц и проверки всех строк нет. Возможны пропуски позиций, количества и цены.
- **Ограниченные проверки.** Названия, номер, валюта и позиции не сопоставляются
  программно с текстом. БИН проверяется по форме и наличию, без контрольной суммы и реестра.
  Даты распознаются в форматах DD.MM.YYYY, YYYY-MM-DD, день + полный месяц + год после
  «от», «Составлено», «Дата документа» либо после '/' в заголовке счёта/акта с №.
  Суммы и НДС требуют поддерживаемых меток; налог проверяется в отдельной строке.
  Неподдерживаемый формат может вызвать ложный пропуск.
- **Воспроизводимость.** Ответ LLM может меняться между запусками. Точное сравнение
  предупреждений и названий считает другую формулировку ошибкой. Оценка на 10 документах
  не характеризует весь поток клиентов.

Реализованы CLI, схемы, API, проверки, тестовый набор и mini-eval. Следующие шаги —
независимый набор документов, сохранение ответов для разбора ошибок и проверка полноты
позиций; добавлять универсальный парсер в рамках этого задания не планировалось.
Наблюдаемые ограничения оставлены явно, вместо изменения эталонов ради метрик.

Документация API: [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs).

## Финальная проверка комплекта

Все файлы кода, настройки-шаблоны, четыре файла тестов, 10 TXT и 10 эталонных JSON
отслеживаются Git; история разработки содержит последовательные коммиты.
Текущий ключ и проверенные шаблоны секретов не найдены в отслеживаемых файлах
и доступной истории; `.env` исключён из Git, ключ в `.env.example` пуст.
Все 38 тестов прошли в рабочем окружении и в отдельной копии отслеживаемых файлов
без `.env`; CLI `--help` и `pip check` также прошли.
Полная установка зависимостей с нуля в новой виртуальной среде не подтвердилась
в этой среде выполнения; проверка отдельной копии использовала уже установленные зависимости.
Поэтому успешная установка по README на чистой машине не заявляется как проверенный факт.
Финальная подготовка меняет только README и REFLECTION, без кода и эталонов,
и не делает запросов к OpenAI API.
